# 0014. 管理画面はビルドの要らない画面を埋め込み、トークンはサーバーのセッションに置く

- 状態: 承認
- 日付: 2026-11-03
- 関連: [design.md](../design.md) 8.4、ADR 0004・0011

## 背景

組織の管理者が自分で使う SaaS にするには、curl ではなく、スマホからも使える管理画面が要る。管理者は IAM でログインする（ADR 0004）。

## 決定

- 画面は HTML・JS・CSS だけで作り、Go のバイナリーに埋め込む。フレームワークもビルドの手順も持たない（依存とサプライチェーンを増やさない、1 つのバイナリーで配る）
- ログインは認可コードフローと PKCE で、MDM がすでに持つ機密クライアント（イントロスペクションに使うもの）でコードをトークンに換える。トークンはブラウザーに渡さず、サーバーのメモリーのセッションに置く。ブラウザーは HttpOnly のクッキーでセッションを示す（BFF の形）
- CSRF はカスタムヘッダー（`X-MDM-UI`）と `SameSite=Strict` で防ぐ。管理の API は CORS を開かない
- XSS は、値を HTML として解釈しない書き方（`textContent`）と、厳しい CSP で防ぐ

## 結果

- ブラウザーにトークンが残らないので、XSS があってもトークンそのものは盗まれない（その画面の中で操作はされうる）
- セッションはメモリーにあるので、再起動するとログインし直す。複数台で動かすときは保存先に移す
- リフレッシュトークンは使わない。トークンの期限（最大 12 時間）が来たらログインし直す
- 画面の機能は API の一部（ポリシーの細かい編集・Apple の証明書・Android の始め方などは後で）

## 検討した代替案

- ブラウザーが公開クライアントとして PKCE でトークンを取る（SPA）：IAM の CORS の設定が要り、トークンがブラウザーに残る
- React などのフレームワーク：画面が大きくなったら考える。いまはビルドの手順を持たないほうが運用が軽い
