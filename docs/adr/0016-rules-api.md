# 0016. ルールの API を imohiyoko/API で定義し、別の口で出す

- 状態: 承認
- 日付: 2026-11-03
- 関連: [design.md](../design.md) 8.6、ADR 0004・0010・0013

## 背景

組織の管理者が、AI のエージェント・自動化のスクリプト・IaC（ルールのファイルを GitHub で管理して plan・apply する）から、ポリシーのルールを変えられるようにしたい。管理の API（`/v1/...`）は画面と人のための形で、契約のファイル（OpenAPI）が無く、丸ごと置き換えると、画面で先に変えたものを黙って消してしまう。

[imohiyoko/API](https://github.com/imohiyoko/api) は、1 つの操作の定義から、公開範囲ごとの口（REST・gRPC）と OpenAPI を作るライブラリ。

## 決定

- ルールの操作（ポリシーの一覧・読む・作る・丸ごと置き換える・ドメインを足す消す、端末の一覧・今すぐ止める・戻す）を imohiyoko/API の `define` で定義し、public の REST として別の口（`rules_api.listen`）で出す。管理の API はそのまま残す
- 認証は管理の API と同じ（設定の鍵か IAM のアクセストークン）。判定は MDM の組織の役割で行う（imohiyoko/API の `port.Authorizer` を MDM で実装する。IAM の `authz:check` は使わない）。役割の無い人のトークンは受けない
- 操作は `rules:read`（組織の管理者・見るだけの人）と `rules:write`（組織の管理者）。対象（組織・ポリシー・端末）の組織で判定する。ほかの組織のもの・無いものは同じ 403 を返し、有るかどうかを見せない。サーバー全体の既定のポリシーは、サーバー全体の管理者しか変えられない
- IaC のために
  - **丸ごと置き換え**（`PUT /v1/policies/{id}`）：書かない項目は空にする。同じ中身なら書かない（何度 apply しても同じ）
  - **試しに送る**（`dry_run`）：保存せず、変わる項目（リストは足すもの・消すもの）を返す（plan）
  - **版**：ポリシーの中身から決まる `version`。`expected_version` を渡すと、ほかの人が先に変えていたら書かずに 412 を返す
  - **書き間違いを断る**：知らない項目は 400
- 契約（`api/rules/openapi/public.json`・`manifest.json`）は定義から作ってリポジトリに置く。食い違うとテストが落ちる（`mdm rules-api gen -out api/rules` で作り直す）
- 呼ぶのは組織の管理者とその自動化なので、エラーのメッセージ（直し方）も見せる。中身の分からないエラーは見せない

## 結果

- AI のエージェントは OpenAPI をそのままツールとして使える
- ファイルを読んで plan・apply する CLI と GitHub Actions の例は、この API の上に後で作る
- 依存に grpc-go と protobuf が入る（imohiyoko/API が求める）
- IAM のサービスアカウントと API キー（iam#151・#152）が使えるようになったら、自動化は設定の鍵の代わりにそれを使う。いまの自動化は、組織に絞った設定の鍵（`admin.tokens` の `org_id`）を使う
- 同時に変えたときは、MDM の中でポリシーの読み書きを 1 つずつにする（1 台で動かす前提。管理の API の置き換えも同じ鍵を使う）

## 検討した代替案

- 管理の API に OpenAPI を手で書く：定義と食い違う。公開範囲ごとの絞り込みとレートリミットも自分で持つことになる
- IAM の `authz:check` で判定する：組織の管理者の役割は MDM が持っている（招待・サインアップ）。二重に持つと食い違う
- 差分だけを送る（PATCH）だけにする：IaC はファイルの中身を正とするので、丸ごと置き換えと版の確かめのほうが合う。AI 向けにはドメインの追加・削除（`edit`）も用意した
