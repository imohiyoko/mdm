# 0018. 端末の正体・持ち主・できることの基礎を、IAM の利用者と端末の証明書で結ぶ

- 状態: 提案
- 日付: 2026-11-16
- 関連: [design.md](../design.md)、ADR 0004・0006・0007・0008・0009・0015

## 背景

「どれが誰の端末で、その端末に何を許すか」を決めたい。いまの MDM には、そのための部品が一部ある。

- **端末の認証**：iPhone・Mac と Windows は、登録のあとの通信を MDM の認証局が発行した端末の証明書（TLS のクライアント証明書）で確かめ、指紋も覚えている（ADR 0006・0007）。Wi-Fi は端末ごとの証明書で入る（ADR 0009）
- **誰の端末か**：端末は 1 つの組織に属し（`Device.OrgID`）、持ち主の人（`Device.PersonID`）を持てる。人は IAM のメールアドレス（`Person.Email`）を持てる（ADR 0008）
- **何を適用するか**：ポリシーは自動のルール → 端末 → 持ち主 → グループ → 組織の既定、の順で決まる。準拠の判定の変化は SSF で IAM に知らせる。RADIUS は組織と準拠を確かめる

足りないものは次のとおり。

1. **持ち主と IAM の利用者のつながりが弱い**：メールアドレスの文字列だけで結んでいる。メールアドレスは変わるし、別の利用者に付け替えられることもある。管理者（`AdminBinding`）は issuer と sub で結んでいるのに、端末を使う人はそうなっていない
2. **登録したのが持ち主か確かめていない**：登録の URL・合言葉・QR コードは管理者が作って渡すだけで、受け取った人が誰でも登録できる。URL が漏れれば、別の人の端末がその人の端末として登録される
3. **端末が本物か確かめていない**：iPhone・Mac の端末の鍵は MDM が作って PKCS#12 で配っている。端末の正体は「そのプロファイルを持っている者」でしかなく、鍵を取り出してほかの機械で使えないことを確かめていない
4. **IAM が端末を確かめられない**：SSF で知らせる端末の ID は不透明な値だけで、IAM のログインに来た人がどの端末を使っているかを、IAM は確かめられない
5. **ネットワークの許可が粗い**：RADIUS は SSID を見ていない。組織の端末で準拠していれば、ポリシーの `wifi` に無い SSID にも入れる

## 決定

### 1. 持ち主は IAM の issuer と sub で結ぶ

- 人（`core.Person`）に `IAMIssuer` と `IAMSubject` を足す。組織の中で同じ組は 1 人だけ
- 結ぶ方法は 2 つ
  - 管理者が管理の API・管理画面で直接付ける（IAM の利用者を知っている会社向け）
  - **人への招待**：管理者が人ごとに 1 回だけ使えるコード（招待と同じく SHA-256 だけを保存、期限付き）を作り、本人が IAM でログインして受けると結ばれる（家族向け。ADR 0011 の招待と同じ形）
- メールアドレスは表示と、SSF の受け手が issuer と sub をまだ扱えないときのためだけに残す
- SSF の受け手（`core.SSFReceiver`）ごとに、利用者の示し方（`email` か `iss_sub`）を持つ。既定は `email`（いまの受け手はそのまま動く）。`iss_sub` の受け手には、持ち主が結ばれていれば `iss_sub` で送り、結ばれていなければ `email` で送る

### 2. 登録のときに持ち主の IAM ログインを求められるようにする

- 端末の登録のコードに「持ち主のログインを求める」を足す。組織の既定と、コードごとの指定を持つ。持ち主のいない端末（共用の端末）には使えない
- 求めるときは、登録の入り口で IAM のログイン（OIDC、管理者のログインと同じ仕組み）を挟み、ログインした利用者が端末の持ち主に結ばれた issuer と sub と同じときだけ登録を進める。違えば止めて、記録に残す。**ログインで新しく結ぶことはしない**（URL を拾った人が自分を持ち主にできてしまうため）
- 機種ごとの入り口
  - iPhone・Mac：登録のプロファイルの URL を Safari で開くので、プロファイルを返す前にログインを挟む
  - Windows：登録の discovery で認証の方式を federated にし、登録の画面（Web の認証の画面）で IAM のログインを挟む。合言葉の方式は残す
  - Android：Android Management API の sign-in の登録（`signinDetails` のログインの URL）で、端末の初期設定の中でログインを挟み、ログインが通ったら登録のトークンを返す
- いま動いている方式（コードだけ）は、選ばなければそのまま使える

### 3. 端末の鍵は端末の中で作り、確からしさを端末ごとに記録する

- 管理している端末（`core.Managed`）に **確からしさ**（`Attestation`）を足す：
  - `hardware`：鍵が端末の安全な場所で作られ、取り出せないことを、メーカーの署名で確かめた
  - `vendor`：メーカーの管理の仕組みが端末を確かめている（Android Management API の端末の情報）が、MDM は鍵を直接確かめていない
  - `none`：確かめていない（いまの iPhone・Mac の PKCS#12、Windows の合言葉の登録）
- 機種ごとの進め方
  - iPhone・Mac：端末の証明書を、プロファイルの PKCS#12 から ACME（`com.apple.security.acme`、鍵は端末に結びつけ、構成証明を付ける）に移す。MDM は ACME のサーバーを持ち、`device-attest-01` で Apple の構成証明を確かめてから証明書を発行する。対応しない古い OS は、いまの方式で `none` のまま登録する。対象の OS の版と条件（監視モードの要否など）は、実装のときに Apple の資料で確かめる
  - Windows：鍵はいまも端末が作っている（CSR を受けて署名する）。まず `none` として記録し、TPM の構成証明（Device Health Attestation）は後の段階で考える
  - Android：Android Management API の端末の情報（セキュリティの状態）を使い、`vendor` として記録する。MDM は端末の鍵を持たない。Android Management API では端末に証明書を入れられない（ADR 0009）ので、Android の端末は MDM の証明書を持たず、4 の mTLS では確かめられない
- 準拠の条件に「確からしさの下限」（`ComplianceRules.MinAttestation`）を足す。下回る端末は `not_attested` の理由で準拠しない。これで RADIUS（準拠を求める設定）と IAM（SSF）にそのまま効く

### 4. 何を許すかは IAM が決め、MDM は確かな端末の情報を渡す

- MDM は「端末に何を適用するか」（ポリシー）を受け持ち、「その端末でどのサービスを使ってよいか」の許可の仕組みを MDM の中に作らない。IAM の許可の判定（ロール・条件付きのアクセス）が、MDM の端末の情報を条件として使う
- そのために、IAM が端末を確かめられる口を MDM に足す
  - 端末の証明書に、端末の ID と組織の ID を URI の SAN（`urn:mdm:device:<id>`・`urn:mdm:org:<id>`）で入れる
  - IAM 向けの問い合わせの API（組織の SSF の受け手ごとの資格情報で認証する）：証明書の指紋か端末の ID から、組織・持ち主の issuer と sub・準拠・確からしさを返す。ほかの組織の端末は返さない。指紋で問い合わせたときは、その指紋が端末の今の証明書（`Managed.CertFingerprints`）のどれかと一致するときだけ返す。認証局の署名が正しくても、外した証明書・管理が外れた端末の証明書は端末として扱わない。いまの実装では、登録し直すと、登録の答えを返す前に前の証明書の指紋を新しいものに置き換える（答えが端末に届かなくても前の証明書は使えなくなる）。ACME に移るときも、新しい証明書を発行した時点で前のものを外す
  - 端末の認証局の証明書を公開の口で出し、IAM が TLS のクライアント証明書（mTLS）で端末を確かめられるようにする
- IAM の側（ログインでの mTLS、ロールの条件に端末の属性を使う）は iam のリポジトリの ADR で決める。IAM は mTLS で受けた証明書を、署名だけでなく必ずこの API で今のものか確かめる
- **Android の端末はこの段階では mTLS で確かめられない**。証明書を入れる道（Android Management API の委任で証明書を入れる仲介のアプリなど）を作るか、IAM が mTLS 以外で確かめるかは、後の ADR（MDM と iam の両方）で決める。それまで Android は、SSF の準拠の知らせと問い合わせの API（端末の ID）だけで扱う

### 5. RADIUS で SSID とポリシーの wifi を照合する

- ルーター（`core.RADIUSClient`）ごとに「SSID を照合する」を持つ。照合するルーターでは、Access-Request の Called-Station-Id（`<MAC>:<SSID>` の形）から SSID を取り、端末の今のポリシーの `wifi` に無ければ入れない。SSID が無ければ入れない
- ポリシーの `wifi` が空なら、照合するルーターにはどの SSID でも入れない（「制限なし」ではない）。管理の API で手で証明書を発行した端末も同じ
- 新しく登録するルーターは、照合するのが既定。いま登録してあるルーターは、照合しないまま残す
- いまのルーターで照合を始めるときの順：(1) 照合しないまま、ルーターが送ってくる SSID を記録で確かめる（照合したら断られる端末も記録に出す）、(2) その SSID を、そのルーターを使う端末のポリシーの `wifi` に入れる、(3) 照合を始める

### 進める順

1. RADIUS の SSID の照合（5）。小さく、ほかに依らない
2. 持ち主を issuer と sub で結ぶ（1）と、SSF の `iss_sub`
3. 登録のときのログイン（2）。iPhone・Mac → Android → Windows の順
4. 確からしさの記録と準拠の条件（3）。まず Android の `vendor` と、ほかの `none` を記録し、iPhone・Mac の ACME はその後
5. IAM 向けの問い合わせの API と証明書の SAN（4）。iam の側の ADR と合わせて進める

## 結果

- 「誰の端末か」は IAM の利用者の issuer と sub で決まり、登録のときに本人がログインすれば、持ち主の取り違え・URL の漏れによる登録を防げる
- 「本物の端末か」は端末ごとの確からしさとして見え、準拠の条件で使える。iPhone・Mac の ACME に移るまでは、iPhone・Mac は `none` のまま
- 「何を許すか」は IAM が決める。MDM の端末の情報が確かになるので、IAM の条件付きのアクセスの条件に使える。MDM の中に、ポリシーとは別の許可の仕組みはできない
- 通信フィルター（DoH・DoT）の端末の秘密はいままでどおり持っている者を信じる。漏れても、その端末のルールが効くだけで、ほかの許可は得られない
- 移行：いまの人・端末・ルーター・SSF の受け手は動き続ける。人の issuer と sub は空のまま、登録のログインは選ばなければ求めない、いまのルーターは SSID を照合しない、いまの SSF の受け手は `email` で受ける

## 検討した代替案

- **メールアドレスのまま結ぶ**：変わる・付け替えられる値で持ち主を決めることになる。管理者と同じく issuer と sub にそろえる
- **登録のときのログインで持ち主を新しく結ぶ**：手間は減るが、登録の URL を手に入れた人が誰でも自分を持ち主にできる。前もって結んだ人と照合するだけにする
- **MDM の中に端末ごとの許可（どのサービスを使ってよいか）の仕組みを作る**：IAM のロール・権限（連携先の権限のカタログなど）と二重になり、どちらで決まったか分かりにくくなる。MDM は事実（持ち主・準拠・確からしさ）を渡すだけにする
- **確からしさを持たず、準拠だけで判断する**：準拠は端末が自分で報告する値で、鍵を取り出した別の機械でも報告できる。端末の正体の確かさは別に持つ
- **iPhone・Mac も SCEP に移す**：鍵は端末で作れるが、構成証明が付かない。ACME（`device-attest-01`）なら鍵が端末の中にあることまで確かめられる
